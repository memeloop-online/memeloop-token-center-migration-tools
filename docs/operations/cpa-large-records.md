# CPA large record operations

Canonical JSON and complete bodies are retained. Digest SHA-256 input remains the sorted schema-v2 record plus newline, including the existing numeric and escaping semantics. No new record format is introduced.

Digest preparation writes canonical JSON incrementally into the existing resumable hash. Its transaction commits cursor, counts and hash state together only after complete records. A canceled or failed record never advances the persisted checkpoint. Blob cache capacity is independent of record acceptance: blobs larger than the cache are decoded for the current record and not retained. Processing remains one record at a time, not one whole session. Decoded semantic JSON and individual CAS blobs still require memory proportional to the largest record; configure the existing container memory and invocation timeout accordingly.

Export retains the existing network fragment reader, SQLite spool and per-record chunk checkpoints. `--max-line-bytes` is an optional operational budget with no compiled 16 MiB ceiling. When omitted it follows the smaller configured download/output budget. `--chunk-bytes` is a checkpoint trigger, not a record acceptance ceiling: a complete record can cross it and is committed before stopping. Configure line/download/output budgets together when choosing smaller limits. Existing spool descriptors retain their original resource settings; use explicit matching budget options when resuming an older spool. This does not change digest checkpoints. Export still validates complete source counts and canonical session digests before publishing output.

Import uses the existing incremental JSONL reader and disk-backed plan. `SESSION_ARCHIVE_MAX_LINE_BYTES` is configurable; the wrapper defaults it to `SESSION_ARCHIVE_MAX_PLAN_BYTES`. There is no compiled 16 MiB line ceiling or compiled 1 GiB plan ceiling in the packaged engine. Plan size and line size remain checked against the operator's configured budgets, with minimum values retained. A single decoded record is materialized for semantic validation and CAS storage; the reader does not accumulate a whole session. Existing match, tenant, provenance, CAS, reference, financial and replay rules remain in force. The separate small plan-row validation concerns locator metadata, not body size.

The Rust reader change is owned here as `ops/runtime-patches/large-record-v1.patch`, applied only to an isolated GHA checkout of the pinned product revision. CI checks the base revision, Cargo.lock, patch SHA and exact changed-file hashes. The sealed runtime retains the patched tree in source.tar. An unpatched older runtime manifest is rejected by the wrapper. No product storage implementation is forked or changed.

## Target importer version dependency

Product PR631 exclusively owns schema127 and requires an importer compatible with its new conversation observation representation. The current product pin `a65097f952e174ac482abe6ff719966fa9d330cb` is not compatible with schema127. Before importing into that schema, coordinate the target importer revision with PR631's owner, update and revalidate this small reader patch against that reviewed revision, and reseal in GHA. This PR does not claim schema127 compatibility or authorize production import, target migration, deployment or merge.

After a reviewed rootfix artifact becomes available, source derivation can resume on the same exclusively bound work copy with the existing PVC identity/fence/checkpoint verification. Completed digests remain valid and are skipped. No source re-copy or checkpoint rewrite is needed. Only digest coverage PASS followed by the existing seal procedure produces an acceptable sealed source. Target import planning then needs explicit compatible runtime identity, space estimates, dry-run counts, replay/conflict behavior and final content/reference/financial reconciliation.
